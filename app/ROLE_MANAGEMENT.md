# Ролі користувачів

Після реєстрації користувач отримує роль **Користувач** (`ROLE_USER`).
Адміністратор може призначити одну із семи ролей у **Мій кабінет → Керування ролями користувачів** (`/admin/users`):

| Роль | Значення |
| --- | --- |
| Користувач | `ROLE_USER` |
| Студент | `ROLE_STUDENT` |
| Викладач | `ROLE_TEACHER` |
| Куратор | `ROLE_CURATOR` |
| Завуч | `ROLE_HEAD_TEACHER` |
| Директор | `ROLE_DIRECTOR` |
| Адміністратор | `ROLE_ADMIN` |

Усі ролі зберігають базовий доступ `ROLE_USER`. Адміністратор успадковує всі перелічені ролі.
Куратор керує власними групами й бачить усіх студентів. Студент бачить свою групу.
Інші навчальні повноваження можна додавати наступними змінами.
Зміна ролі замінює попередню призначену роль. Доступ до перегляду та зміни ролей має лише адміністратор.
Після зміни ролі активний сеанс користувача завершується на наступному захищеному запиті;
для роботи з оновленими правами потрібно увійти повторно.

## Меню після входу

Кабінет і сторінки адміністратора використовують спільне бічне меню замість інформаційного блоку зі сторінок входу.
Бургер перемикає меню між іконками з підписами та лише іконками. Стан зберігається в браузері;
на вузькому екрані за замовчуванням показуються іконки. Усі пункти мають доступні назви й підказки.

- Кожна роль: «Мій кабінет» та вихід із системи.
- Студент: «Моя група», «Мої дисципліни», «Мої викладачі».
- Викладач: «Мої групи», «Мої дисципліни».
- Куратор: «Мої групи», «Усі студенти».
- Адміністратор: керування користувачами, усі групи та студенти.
- Для завуча та директора додаткові пункти ще не визначено.

Маршрут `/student/group` показує групу студента, її куратора та список одногрупників.
Навчальні маршрути `/student/disciplines`, `/student/teachers`,
`/teacher/groups`, `/teacher/disciplines` наразі показують початкові сторінки без даних.
Сервер перевіряє відповідну роль; адміністратор має доступ до всіх цих маршрутів.

## Список користувачів

Маршрут `GET /admin/users` доступний лише адміністратору. Сторінка показує ID, ім’я,
email, призначену роль, групу, наявність пароля та дату створення облікового запису.
Розмір сторінки: 10, 20 (за замовчуванням), 50 або 100 записів. Порядок — за ID, від меншого до більшого.

Фільтри можна поєднувати: точний ID, частина імені (`fullName`), частина email (`email`),
призначена роль (`role`), ID групи (`studentGroup`), наявність пароля (`password=set` або `password=empty`),
початкова і кінцева дати створення (`createdAtFrom`, `createdAtTo`, формат `YYYY-MM-DD`).
Кінцева дата включає весь день. Фільтр «Користувач» знаходить акаунти без іншої призначеної ролі.
Паролі та їхні хеші в інтерфейсі не відображаються.
Фільтри й розмір сторінки зберігаються в URL під час переходів між сторінками;
застосування фільтрів починає перегляд із першої сторінки. Некоректні значення повертають HTTP 422.

Приклад: `/admin/users?role=ROLE_STUDENT&perPage=10&page=2`.

## Групи та куратори

Сутність `Group` зберігається в узгодженій таблиці `groups`: ID, назва, куратор-власник та дата створення.
Зв’язок `users.group_id` дозволяє студенту належати лише до однієї групи; таблиця зв’язку не потрібна.
Міграція `Version20261019110000` створює таблицю, індекси та зовнішні ключі.
Наявні користувачі після міграції не належать до жодної групи.

| Маршрут | Призначення |
| --- | --- |
| `GET /curator/groups` | Власні групи; для адміністратора — всі групи, по 20 на сторінці |
| `GET, POST /curator/groups/new` | Створення групи з поточним користувачем як власником |
| `GET /curator/groups/{id}` | Склад власної групи, по 20 студентів на сторінці |
| `GET /curator/students` | Усі студенти, пошук за ID/ім’ям/email, фільтр «Лише без групи», розміри 10/20/50/100 |
| `GET, POST /curator/students/{id}/assign` | Вибір власної групи та зарахування студента |
| `POST /curator/groups/{id}/students/{studentId}/remove` | Вилучення студента з власної групи без видалення акаунта |
| `GET /student/group` | Власна група студента |

Доступ до `/curator/*` мають лише куратори й адміністратори. Куратор не може переглядати склад
або змінювати чужу групу, навіть підставивши її ID у запиті. Адміністратор може керувати всіма групами.
Створення групи не дозволяє підмінити її власника. Усі форми змін захищені CSRF.
Зарахування виконується умовним SQL-оновленням: студент має залишатися студентом і бути без групи.
Це також запобігає неявному переведенню та конфлікту двох одночасних зарахувань.
Якщо адміністратор змінює роль студента на іншу, зв’язок із групою прибирається.

Застосування міграції в налаштованому середовищі:

```bash
docker compose exec -T app php bin/console doctrine:migrations:status
docker compose exec -T app php bin/console doctrine:migrations:migrate --dry-run --no-interaction
docker compose exec -T app php bin/console doctrine:migrations:migrate --no-interaction
docker compose exec -T app php bin/console doctrine:schema:validate
```

Відкат `Version20261019110000` прибирає зв’язки студентів і таблицю груп, зберігаючи акаунти:
`docker compose exec -T app php bin/console doctrine:migrations:execute 'DoctrineMigrations\Version20261019110000' --down`.

## Перший адміністратор

Міграція `Version20261019100000` створює адміністратора в наявній таблиці `users`.
Передайте `ADMIN_EMAIL` і `ADMIN_PASSWORD` у середовище процесу міграції.
Пароль повинен містити від 12 до 72 байтів; у базу записується лише bcrypt-хеш.
Наявний обліковий запис із такою адресою не змінюється: міграція зупиниться з поясненням.

Приклад для Bash на сервері з Docker Compose (із кореня репозиторію):

```bash
read -r -p 'Email адміністратора: ' ADMIN_EMAIL
read -r -s -p 'Пароль адміністратора: ' ADMIN_PASSWORD
export ADMIN_EMAIL ADMIN_PASSWORD
docker compose exec -T -e ADMIN_EMAIL -e ADMIN_PASSWORD app php bin/console doctrine:migrations:status
docker compose exec -T -e ADMIN_EMAIL -e ADMIN_PASSWORD app php bin/console doctrine:migrations:migrate --dry-run --no-interaction
docker compose exec -T -e ADMIN_EMAIL -e ADMIN_PASSWORD app php bin/console doctrine:migrations:migrate --no-interaction
unset ADMIN_EMAIL ADMIN_PASSWORD
```

Після міграції увійдіть з указаними email і паролем. Подальші міграції цих змінних не потребують.
Міграція створення адміністратора незворотна: автоматичний відкат міг би видалити робочий обліковий запис із пов’язаними даними.
Щоб прибрати доступ, інший адміністратор може змінити його роль через інтерфейс.

## Перевірки

Функціональні тести використовують окрему SQLite-базу `var/auth-test.db` і перевіряють
реєстрацію, усі сім ролей, заборону зміни ролей для неадміністраторів, CSRF та відхилення невідомих ролей.
Для запуску потрібні dev-залежності Composer, PHP, сумісний із `composer.lock`, та розширення PDO SQLite:

```bash
docker compose exec -T app php bin/phpunit
docker compose exec -T app php bin/console lint:yaml config
docker compose exec -T app php bin/console lint:twig templates
```
